# OpenTUI TestDriver Setup

## Overview
OpenTUI is a terminal UI library that doesn't produce a traditional web application. However, the project documentation sites (opencode.ai, terminal.shop) are web-based and can be tested. Additionally, if there are web-based demos or documentation, those should be the test targets.

## Setup Steps

### 1. No Build Workflow Needed
This project is a library, not a deployable web application. The build process (`bun run build`) compiles the TypeScript packages but doesn't produce a web application to deploy. Therefore, no build workflow is needed.

### 2. TestDriver Workflow Setup
Since there's no build step required, the TestDriver workflow uses standard triggers (pull_request, push, workflow_dispatch) rather than workflow_run.

The workflow will test the external documentation sites:
- https://opencode.ai
- https://terminal.shop

### 3. Generate Tests Workflow
The generate workflow will create exploratory tests for the documentation sites. It uses workflow_dispatch for manual triggering.

### 4. Environment Variables
Add the following secret to your GitHub repository:
- `TD_API_KEY`: Your TestDriver API key (get from https://app.testdriver.ai)

The TD_WEBSITE variable will be set to the documentation URLs in the workflows.

### 5. Running Tests

**Manual Test Generation:**
```bash
TD_WEBSITE=https://opencode.ai TD_API_KEY=your_key npx testdriverai@latest generate web 5
```

**Running Tests Locally:**
```bash
TD_WEBSITE=https://opencode.ai TD_API_KEY=your_key npx testdriverai@latest run testdriver/generate/*.yaml
```

**Via GitHub Actions:**
1. Tests run automatically on pull requests and pushes
2. Generate new tests via Actions tab → "Generate TestDriver Tests" → Run workflow

### 6. Test Focus Areas
- Documentation site navigation and content
- Getting started guides and code examples
- Installation instructions
- API documentation pages
- Example demos (if available)
- Links to external resources (npm, GitHub, etc.)

## Rationale

This approach is recommended because:

1. **No Build Workflow Needed**: OpenTUI is a TypeScript library for building terminal UIs, not a web application. The `bun run build` command compiles TypeScript to JavaScript for npm distribution, but doesn't produce a deployable web app. Therefore, no build workflow is required.

2. **Testing External Documentation**: The project references two web properties (opencode.ai and terminal.shop) that are built on top of OpenTUI. These are the appropriate test targets for web testing. The TestDriver workflow uses a matrix strategy to test both sites.

3. **Simple Workflow Chain**: Since no build is needed, the TestDriver workflow uses standard triggers (pull_request, push, workflow_dispatch) rather than workflow_run. This simplifies the setup and makes tests run immediately on code changes.

4. **Flexible Test Generation**: The generate workflow allows choosing which site to test and how many tests to generate. This is useful since the two sites may have different functionality and user flows.

5. **Library vs Application**: This project is a library that developers integrate into their own applications. Testing the library itself would require testing its API and functionality in a consumer application, which is beyond the scope of web testing. Instead, we test the web-based documentation and showcase sites that demonstrate the library's capabilities.

6. **Future Expansion**: If the project adds web-based demos or examples (e.g., a WebAssembly-based terminal emulator running in the browser), those could be added as additional test targets in the matrix strategy.
